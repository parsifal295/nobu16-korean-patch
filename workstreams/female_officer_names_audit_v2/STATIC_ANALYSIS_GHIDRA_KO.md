# Ghidra MCP 정적 분석 기록 — 여성 무장 이름 v2

이 기록은 런타임 실행 없이 Ghidra MCP로 확인한 이름 조합·레코드·저장 경로의
근거다. 게임 설치본은 수정하지 않았다.

## 확정한 표시 및 레코드 경로

| 기능 | 정적 근거 | 결론 |
|---|---|---|
| 조합 이름 생성 | `FUN_1405F40D0` | 레코드 `+0x0C/+0x0E`를 우선 사용하고, 조건에 따라 `+0x08/+0x0A`로 대체한다. |
| 문자열 ID 해석 | `FUN_1409F9BE0` | ID `<= 0x22DB`를 문자열 테이블/DB 콜백으로 해석한다. |
| 이름 포매팅 | `FUN_140C93CD0` | `%s%s`, `%s %s`, `%s\n%s` 형식이 모두 있어, component 단순 이어붙이기만으로 공백 규칙을 단정할 수 없다. |
| 실제 인물 조회 | `FUN_1405DBD30` → `FUN_140684A40` | `id < 0x17F5`에서 루트의 `+0xE8 + id*8` 포인터 테이블을 조회한다. |
| 실제 인물 생성 | `FUN_14068FDB0` → `FUN_140670AC0` | 루트는 동적 할당되며, 역사 인물 레코드 6,133개를 각 `0x270` 바이트로 생성한다. |
| 레코드 생성자 | `FUN_14057E730` | 조합 이름 필드가 레코드 `+0x08/+0x0A/+0x0C/+0x0E`에 있다는 구조를 확인했다. |

따라서 조합형 UI는 `msgev`의 전체 이름 한 줄을 그대로 표시하는 경로가 아니라,
런타임 인물 레코드의 component ID를 해석해 포매팅하는 경로다.

## 원본 편집 데이터와의 관계

`HDATA000.se_n16_SC`는 `NOBU16HEDIT_V1`/`NB16__EDITH_V1` 형식의 편집용
레코드 2,400개(헤더 `0x14`, stride `0x386`)다. `FUN_140BE14C0`가 이 형식을
읽는 것을 확인했지만, 이것은 능력·분류 등의 편집 데이터이며 실제 런타임 이름
component 필드를 직접 담지 않는다. 이 파일의 `+0x08/+0x0A/+0x0C/+0x0E`를
런타임 레코드의 이름 ID로 읽는 방식은 오탐이므로 사용하지 않았다.

## 저장·고정 데이터 역추적 결과

`FUN_1406AADB0`는 저장 스트림을 읽을 때 역사 인물 레코드의 virtual slot
`+0x28` (`FUN_1405B9C50`)로 역직렬화한다. 이 함수는 해당 레코드의 이름 관련
16비트 필드를 순서대로 처리한다. 반면 기본 고정 데이터 경로
`FUN_1406B6BD0` → `SCENARIO_PK/fixdataPK.n16` → `FUN_1406A8540`는 인물
레코드의 slot `+0x30` 상태 검증을 사용하며, 기본 이름 ID 표를 채우는 경로가
아니다.

보유 저장 파일도 교차 대조했다. 저장 파일은 기본 인물명 component 표의 신뢰할
수 있는 정적 원본이 아니며, 확인된 오이치·히메 anchor ID 배열도 저장 원문에서
나오지 않았다. 따라서 저장 파일의 우연한 바이트열이나 편집 레코드로 나머지
여성 무장의 실제 ID 조합을 추정해 전역 치환하지 않는다.

## 공유 범위 재감사와 후보 빌드 범위

처음의 11개 component 후보는 배포 근거가 아니었다. SC `msgdata`의 component
원문 토큰이 역사 인물명(0–2,206) 전체에 나타나는 범위와, 그 모든 행의 직접
한국어 `msgev` 표기를 다시 대조했다. 이는 실제 런타임 레코드 ID 표를 복원한
것은 아니지만, 전역 component 수정으로 다른 무장 이름을 훼손할 수 있는지를
판단하는 보수적 상한이다.

| component | 역사 인물명 원문 토큰 범위 | 결론 |
|---:|---:|---|
| 287 | 1 | 네네만 해당; 유지 |
| 376 | 125 | 전원 `요시` 표기; 공유 효과까지 검증하여 유지 |
| 386 | 7 | 메고히메는 `386+2082`; 나머지 6명은 `386` 없는 별도 exact pair로 검증되어 유지 |
| 434 | 1 | 오바이인만 해당; 유지 |
| 773 | 1 | 조케이인만 해당; 유지 |
| 791 | 7 | 전원 `후유` 표기; 공유 효과까지 검증하여 유지 |
| 2081, 6708 | 각 1 | 기초만 해당; 유지 |
| 2082 | 10 | 전원 히메 계열; 사용자 지시대로 `히메` 통일 |
| 2083 | 5 | 오이치 관측 anchor; 나머지 4명은 `2083` 없는 별도 exact component pair로 검증되어 유지 |
| 2087 | 1 | 묘큐만 해당; 유지 |

따라서 배포 가능한 정적 안전 후보 v2는 다음 11개를 포함한다.

`287, 376, 386, 434, 773, 791, 2081, 2082, 2083, 2087, 6708`

메고히메는 exact pair `386+2082`를 `메고히메`로 고친다. 토큰 겹침으로 잡힌
나머지 6명은 `387+2223`, `387+1947`, `394+1031/7997`, `879+2706`,
`879+957/7387`, `879+1841`의 별도 exact pair이며 `386`을 쓰지 않는다.
오이치는 관측 조합 anchor `[62, 2083]`를
`오이치`로 고치며, 토큰 겹침으로 잡힌 이치카와·이치하시·도치 2명은 각각
`573+1661/7764`, `572+2371`, `596+2016`, `596+2447`의 별도 exact pair임을
정적으로 확인했다.

v1 11개 후보 빌더는 의도적으로 실행 차단했으며, v2 후보만 설치본 밖에서
생성한다. v2는 변경되지 않은 모든 문자열, 메시지 테이블 왕복, 압축 래퍼, 및
위 역사 인물명 범위 검증을 통과했다.

나머지 14개 정적 불일치 및 다의성 항목은 실제 런타임 레코드별 ID 표를 정적으로
복원하지 못한 상태에서 component를 수정하면 다른 인물에 영향을 줄 수 있으므로
보류한다. 상세 목록은 [전수 감사](ALL_FEMALE_OFFICER_NAME_AUDIT_KO.md) 및
[남은 조합 감사](REMAINING_COMPONENT_COMBINATION_AUDIT_KO.md)를 따른다.
