# Steam Deck 컨트롤러 경로의 PC 실행 파일 이식 가능성 조사

## 결론

이식 가능하며 실게임에서 검증했다. Steam Deck 실행 파일에서 컨트롤러
드라이버 전체를 PC 실행 파일로 복사할 필요는 없다. 현행 PC 실행 파일에도
이미 같은 XInput 장치 열거, 상태 폴링, 버튼/축 변환 코드가 들어 있다.

최종 분리점은 PC 전역 입력 모드 값 `RVA 0x217D75C`이다. 이 값을 `1`로
초기화하면 PC 실행 파일이 XInput 장치를 등록하고 패드 입력을 정상 처리한다.
다만 상위 프레임 함수 `0x140571440`이 이 값에 따라 마우스 경로와 패드 경로
중 하나만 선택하므로, 같은 EXE에서 값을 계속 `1`로 두면 마우스 입력이
비활성화된다.

따라서 v0.90.0 패처는 컨트롤러 지원을 선택형으로 제공한다.

- `사용 안 함`: `NOBU16PK.exe`만 설치
- `실험적 지원 사용`: 일반 `NOBU16PK.exe`와 컨트롤러 초기화 스텁을 넣은
  `NOBU16PK_XINPUT.exe`, `steam_appid.txt`를 함께 설치

두 파일은 같은 게임 리소스와 PC 해상도 설정을 사용한다. XINPUT판도
Steam Deck 해상도 판정 함수 자체를 변경하지 않으므로 Windows에서
`3840 x 2160` 설정으로 실행됐고, 별도 상주 프로그램이나 DLL이 필요 없다.

비 Steam 바로가기는 자체 임의 AppID를 주입하므로, EXE만 등록하면
`SteamAPI_Init() failed`가 발생한다. 게임 루트에 정품 AppID `1336980`을
기록한 `steam_appid.txt`를 함께 설치하면 같은 바로가기에서 정상 실행된다.
이는 외부 프로그램이 아니라 Steamworks 초기화용 8바이트 표식 파일이다.
사용자는 `NOBU16PK_XINPUT.exe`를 Steam에 비 Steam 게임으로 등록하고 해당
바로가기의 Steam Input만 활성화하면 된다. 패드는 게임 시작 전에 연결한다.

실제 분리점은 여러 기능이 함께 사용하는 Steam Deck 런타임 판별이다.
두 실행 파일은 모두 Steamworks `ISteamUtils::IsSteamRunningOnSteamDeck()`와
일치하는 판별 함수를 호출한다. 이 반환값이 참이면 다음 동작들이 한꺼번에
활성화된다.

- XInput 장치에 대한 Steam Deck 전용 입력 보정
- 해상도 `1280 x 720` 강제
- 창 모드 값 `2` 강제
- Win32 텍스트 입력 대신 Steam의 게임패드/플로팅 키보드 경로 사용
- 일부 URL 및 동영상 경로의 Steam Deck 처리

따라서 Steam Deck 판별 함수 자체를 항상 참으로 만드는 전역 패치는
목표에 맞지 않는다. PC 해상도 설정 경로는 그대로 두고, 입력 관리자 안의
Steam Deck 조건만 선택적으로 참으로 만드는 것이 첫 번째 구현 후보이다.

최초 정적 패치 후보는 Steam 설치본에서 시험했지만 효과가 없었다. 후속
Ghidra 분석에서 해당 두 호출은 XInput 장치를 생성하거나 등록하는 초기화
지점이 아니라, 이미 선택된 장치의 상태 비트를 보정하는 후처리임을
확인했다. 다음 단계는 Steam Input이 PC 실행 파일에 가상 XInput 장치를
제공하는지와 상위 장치 등록 경로를 런타임에서 확인하는 것이다.

## 조사 기준 바이너리

Steam 설치본의 현재 `NOBU16PK.exe`는 이미 패치된 67 MB 파일이므로 직접
비교 기준에서 제외했다. 같은 Steam 빌드의 보존된 원본 PC 실행 파일과
Steam Deck 실행 파일을 Steamless로 언팩한 결과를 Ghidra에서 비교했다.

| 구분 | 크기 | SHA-256 |
| --- | ---: | --- |
| 원본 PC `NOBU16PK.exe` | 31,978,264 | `29BC1ED66D27B9AEF5EB6CE3D126BA2BDBF86099E12B09615FE9F988F41E2246` |
| 원본 SD `NOBU16PK_SD.exe` | 31,969,048 | `6218F8987404BB20E1771D4E7BA032405DB9788C212F5E89F96B9AEFADA21FCD` |
| 언팩 PC | 31,747,848 | `BC885875A5E4288E5A1A424D99974F6F215777C03569C7EA707FDE63BDBC2B39` |
| 언팩 SD | 31,738,632 | `2411BF032F382FCD200D522E87A6D3551322CA28408518439003EB443CDF4A5B` |

설치된 게임의 Steam 앱 빌드 ID는 조사 시점에 `18823764`였다.

## PE 및 입력 계층 비교

두 언팩 실행 파일은 모두 x64 PE이며 같은 세 XInput 심볼을
`XINPUT1_3.DLL`에서 가져온다.

- `XInputGetState` (ordinal 2)
- `XInputSetState` (ordinal 3)
- `XInputEnable` (ordinal 5)

PC 실행 파일의 `.text`가 SD 실행 파일보다 `0x2000` 바이트 크지만,
추가 크기가 컨트롤러 모듈의 유무를 뜻하지는 않는다. 다음 핵심 함수는
전역 주소와 재배치된 내부 호출 주소를 제외하면 같은 동작을 한다.

| 역할 | PC VA | SD VA | 확인 내용 |
| --- | --- | --- | --- |
| XInput 장치 열거/생성 | `0x140FDFA80` | `0x140FE0000` | 최대 4개 패드 탐색, `XInputGetState`, `0x2A8` 바이트 장치 객체 생성 |
| XInput 상태 폴링/변환 | `0x140FE0720` | `0x140FE0CA0` | 진동 상태 전달, `XInputGetState`, 버튼·트리거·스틱을 내부 상태로 변환 |
| Steam Deck 판별 | `0x1409C07A0` | `0x1409C02E0` | Steamworks 인터페이스 vtable `+0x110`의 bool 메서드 호출 |
| 그래픽 설정 로드 | `0x1408B0000` | `0x1408AFC80` | 판별 결과에 따라 레지스트리 설정 또는 `1280 x 720`/모드 `2` 선택 |
| 입력 장치 후처리 | `0x140C5DE90` | `0x140C5E0B0` | 내부 키 코드 `0x27`과 `0`의 Deck 전용 상태 플래그 보정 |

Steamworks 공식 문서상 `ISteamUtils::IsSteamRunningOnSteamDeck()`는 Steam이
Steam Deck 또는 다른 SteamOS 기기에서 실행 중인지를 반환한다.

<https://partner.steamgames.com/doc/api/ISteamUtils#IsSteamRunningOnSteamDeck>

## 해상도 고정 경로

PC `0x1408B0000`과 SD `0x1408AFC80`은 같은 구조이다.

```text
if IsSteamRunningOnSteamDeck():
    width       = 1280
    height      = 720
    window_mode = 2
else:
    width       = Configs/WIDTH  (기본 1600)
    height      = Configs/HEIGHT (기본 900)
    window_mode = Configs/WINDOW_MODE
```

즉 해상도 고정은 SD 실행 파일에만 존재하는 별도 구현이 아니라 두 실행
파일에 공통으로 들어 있는 Steam Deck 런타임 분기이다.

## 선택적 입력 패치 후보

PC 입력 관리자 `0x140C5DE90` 안에서 Steam Deck 판별을 호출하는 두 지점이
첫 번째 최소 패치 후보이다.

| 호출 VA | 언팩 파일 오프셋 | 원본 5바이트 | 후보 5바이트 | 의미 |
| --- | --- | --- | --- | --- |
| `0x140C5E256` | `0x00C5D656` | `E8 45 25 D6 FF` | `B8 01 00 00 00` | 내부 키 코드 `0x27`의 Deck 입력 보정 활성화 |
| `0x140C5E292` | `0x00C5D692` | `E8 09 25 D6 FF` | `B8 01 00 00 00` | 내부 키 코드 `0`의 Deck 입력 보정 활성화 |

후보 바이트는 `call IsSteamRunningOnSteamDeck`을 `mov eax, 1`로 바꾸며
명령 길이를 그대로 유지한다. 해상도 함수의 판별 호출은 변경하지 않으므로
PC의 `WIDTH`, `HEIGHT`, `WINDOW_MODE` 설정 경로가 유지된다.

이 두 지점은 입력 장치 목록과 내부 입력 객체를 순회하고 장치의 입력 상태
플래그를 보정하는 함수 안에 있다. XInput 장치 열거와 폴링은 원래부터
항상 존재하므로, 우선 이 두 분기만 활성화하는 것이 가장 작은 실험이다.

## 전역 판별 패치를 피해야 하는 이유

PC 판별 함수 `0x1409C07A0`에는 입력 이외에도 최소 19개의 코드 참조가 있다.
대표적인 참조는 다음과 같다.

- `0x1408B0063`, `0x1408B0112`: `1280 x 720`, 창 모드 `2` 강제
- `0x1408B3519`: Steam Deck에서 그래픽 설정 저장 생략
- `0x1408C1EA7` 계열: Win32 편집 컨트롤 대신 Steam 플로팅 키보드 사용
- `0x140ACCE29`, `0x140ACCE71`: SD용 동영상 경로 조립
- `0x140571E22`, `0x140ED5596`: Steam Overlay URL 처리
- `0x140C5E256`, `0x140C5E292`: 입력 장치 후처리

판별 함수 본문을 항상 참으로 패치하면 컨트롤러 외의 모든 동작이 함께
바뀌며, 사용자가 피하려는 해상도 고정도 다시 발생한다.

## v0.90.0 Rust 패처 통합안

v0.90.0 패처는 보호된 순정 EXE를 검증한 뒤 정규화된 언팩 기준본으로
변환하고, 레시피의 정적 패치들을 순서대로 적용한다. 각 사이트는
`offset`, `before_hex`, `after_hex`로 정의되며, 원본 바이트가 다르면
전체 트랜잭션을 중단한다. 마지막에는 PE 체크섬과 선언된 최종 크기 및
SHA-256을 다시 검증한다.

두 컨트롤러 후보 사이트는 기존 v0.90.0 가로형 12개 패치 및 세로형 8개
패치와 겹치지 않는다. 현재 v0.90.0 가로형·세로형 최종 EXE에서도 두
사이트의 원본 바이트가 그대로 확인되었다.

| 레이아웃 | v0.90.0 최종 크기 | v0.90.0 최종 SHA-256 | 두 사이트 상태 |
| --- | ---: | --- | --- |
| 가로형 | 67,024,896 | `7A0DF96C72A93F551F283EF14F06159F50E6A265A3BAC9C14151A1C2895D4DA0` | 두 원본 5바이트 일치 |
| 세로형 | 31,748,608 | `9507DBEDDBCA9CE7202C6818A2621C52CA4B6DED8271626B0F5D90AF93825189` | 두 원본 5바이트 일치 |

가장 작은 통합은 각 레시피 끝에 `013`을 추가하는 것이다.

```json
{
  "id": "013",
  "name": "Enable PC controller input without Deck display policy",
  "sites": [
    {
      "name": "force Deck input postprocessing for internal key 0x27",
      "offset": 12965462,
      "before_hex": "E84525D6FF",
      "after_hex": "B801000000"
    },
    {
      "name": "force Deck input postprocessing for internal key 0",
      "offset": 12965522,
      "before_hex": "E80925D6FF",
      "after_hex": "B801000000"
    }
  ]
}
```

다만 현재 패처 모델은 레시피에 들어 있는 모든 패치를 무조건 적용하며
개별 패치 선택 기능은 없다. 따라서 배포 방식은 다음 둘 중 하나가 된다.

1. 컨트롤러 지원을 기본값으로 정하고 가로형·세로형 레시피에 `013`을
   항상 포함한다. 코어 코드 변경이 거의 없지만 검증 전 기능을 전 사용자에게
   강제하게 된다.
2. 권장안으로, 기존 일반 가로형·세로형 번들은 유지하고 `013`을 포함한
   컨트롤러 가로형·세로형 번들을 추가한다. 공통 리소스 번들은 그대로
   공유하며, 메뉴에서 레이아웃과 컨트롤러 실험 기능을 선택한다.

선택형 배포는 정적 번들이 총 네 개가 된다.

- 세로형 일반
- 세로형 + 컨트롤러
- 가로형 일반
- 가로형 + 컨트롤러

패처 내부에서 임의 바이트 토글을 허용하기보다 각 변형을 별도의 서명 번들과
고정 최종 해시로 다루는 편이 v0.90.0의 검증·백업·원자적 적용 구조를
보존한다. 이미 적용된 변형에서 다른 변형으로 바꿀 때는 우선 원본 복원 후
새 변형을 적용하는 흐름이 가장 단순하다.

컨트롤러 경로는 실게임에서 작동을 확인했지만 마우스와 상호 배타적이므로
메뉴에는 `실험적 지원 사용`으로 표시하고 일반 지원을 기본 선택으로 둔다.

두 입력 사이트만 적용한 후보를 배포했다. 후보는 Steam 경로 밖에서 먼저
구성하고 허용된 사이트와 PE 체크섬 필드 외에 변경이 없음을 확인한 뒤,
원본 백업을 생성하는 원자적 교체로 설치했다.

이 기동 확인은 EXE 로드와 초기 실행만 검증한다. 실제 컨트롤러의 버튼,
스틱, 포커스 및 아이콘 전환은 아직 판정하지 않았다. 확인 후 게임
프로세스는 종료했으며 현재 실행 중이 아니다.

### 최초 후보 실패 및 원인 정정

사용자 실게임 확인 결과 위 두 사이트 후보로는 컨트롤러 조작이 활성화되지
않았다. 후속 Ghidra 비교 결과는 다음과 같다.

- PC `0x140C5DE90`과 SD `0x140C5E0B0` 입력 관리자 함수는 주소 재배치를
  제외하면 같은 흐름이다.
- PC `0x140FDFA80`/`0x140FE0720`과 SD
  `0x140FE0000`/`0x140FE0CA0`의 XInput 생성·폴링 함수도 같은 흐름이다.
- 두 실행 파일 모두 Steam Deck 판정 호출점이 23개이며 역할이 일대일로
  대응한다.
- 패치한 두 호출은 장치 생성 전 조건이 아니라, 이미 존재하는 장치의 내부
  상태 비트를 보정하는 후처리이다.
- 실패 확인 뒤 Windows에서 `XInputGetState`를 직접 호출했을 때
  XInput 1.3과 1.4의 슬롯 0–3이 모두 `1167`
  (`ERROR_DEVICE_NOT_CONNECTED`)을 반환했다.

따라서 최초 실패의 직접 원인은 “두 후처리 분기만으로 입력 장치를 활성화할
수 없다”는 것이다. 현재 가장 유력한 상위 원인은 Steam Input이 PC 실행
파일에 가상 XInput 장치를 제공하지 않았거나, 시험 시 컨트롤러가 Windows
XInput 장치로 연결되지 않은 경우이다. 실제 패드가 연결된 상태에서
SD/PC를 같은 Steam 실행 방식으로 번갈아 실행하며 XInput 슬롯 변화를
측정해야 두 경우를 구분할 수 있다.

실패 후보는 확인 직후 검증된 v0.90.0 가로형 백업으로 원복했다. 현재 Steam
설치 `NOBU16PK.exe`의 SHA-256은 다시
`7A0DF96C72A93F551F283EF14F06159F50E6A265A3BAC9C14151A1C2895D4DA0`이다.
실패 후보는 같은 백업 폴더의
`NOBU16PK.failed-controller-candidate.exe`로 보존했다.

## 최종 런타임 검증과 분리 배포

실제 XInput 슬롯 0이 연결된 상태에서 PC 전역 입력 모드 값을 런타임으로
`1`로 바꾸자 내부 컨트롤러 장치 수, 목록, XInput 마스크가 모두 `1`이
되었고 사용자가 패드 조작 성공을 확인했다. 같은 동작을 실행 파일 초기화
스텁으로 고정한 결과도 외부 프로그램 없이 재실행 후 패드 입력에 성공했다.

이후 마우스 입력이 동작하지 않는 회귀를 확인했다. 이는 패치 오류가 아니라
상위 프레임의 의도된 상호 배타 분기였다. 사용자 결정에 따라 단일 EXE의
동시 입력은 중단하고 일반판과 XINPUT판을 병행 설치하는 방식으로 전환했다.

| 레이아웃 | 일반 EXE SHA-256 | XINPUT EXE SHA-256 |
| --- | --- | --- |
| 가로형 | `7A0DF96C72A93F551F283EF14F06159F50E6A265A3BAC9C14151A1C2895D4DA0` | `6EDB65ECFBEBC73C4211E86A3E6BD286F075DD4AD8CECB16E58448612877AF6A` |
| 세로형 | `9507DBEDDBCA9CE7202C6818A2621C52CA4B6DED8271626B0F5D90AF93825189` | `9C0F5FBAEEA02BA47D21C1286664119FE58FADD80CA200DFB7A69AADABF5C276` |

Steam 설치 경로에는 가로형 일반판을 변경하지 않은 채
`NOBU16PK_XINPUT.exe`를 추가했다. `_PAD` 임시 이름은 제거했다.

- 선택 해상도: `3840 x 2160`
- 해상도 변경 후 완전 프로세스 종료·재실행: 완료
- XINPUT판 프로세스명과 창 생성: 확인
- XINPUT판 패드 입력: 같은 바이트의 선행 실게임 후보에서 사용자 확인
- 일반판 마우스 입력: 실행 파일 해시는 회귀 전 검증본과 동일

## v0.90.0 패처 최종 통합

Rust 패처 엔진을 `0.2.0`으로 올리고 목표별 `source_relative_path`와
고정 재료용 `material_path`를 추가했다. 통합 메뉴는 다음 순서로 동작한다.

1. 이름 쓰기 방향: 세로형 / 가로형
2. 컨트롤러 지원: 사용 안 함 / 실험적 지원 사용
3. 적용: 선택 내용 확인 후 실행

일반 번들은 `NOBU16PK.exe`만 정적패치 012까지 적용한다. 실험적 번들은
하나의 검증된 순정 `NOBU16PK.exe`에서 다음 세 목표를 같은 트랜잭션으로
만든다.

1. 일반 `NOBU16PK.exe`: 정적패치 012까지 적용
2. `NOBU16PK_XINPUT.exe`: 같은 레시피에 정적패치 013을 추가 적용
3. `steam_appid.txt`: 비 Steam 바로가기용 정품 AppID `1336980`

XINPUT판과 AppID 표식은 설치 기록에서 생성 파일로 표시한다. 복구 시
일반판은 검증된 백업으로 복원하고 두 생성 파일은 삭제한다. 세로/가로와
일반/실험적 지원을 조합한 네 서명 번들을 격리 복제본에서 각각 적용하고,
목표 해시, 이미 적용 상태, 복구 및 생성 파일 삭제를 검증했다. 구성 변경
시에는 먼저 원본 복구를 실행한다.

## 현재 판정

- 기술적 가능성: **가능, 실게임 패드 입력 검증 완료**
- 구현 성격: 컨트롤러 코드 이식이 아니라 **PC 내장 XInput 경로 활성화**
- 단일 EXE 마우스+패드 동시 지원: **입력 모드 상호 배타 분기로 채택하지 않음**
- 최종 배포: **일반 지원 / 일반 EXE + `NOBU16PK_XINPUT.exe` 병행 중 선택**
- 외부 런처·상주 프로그램·DLL: **불필요**
- AppID 처리: **실험적 지원 선택 시 `steam_appid.txt` 자동 생성**
- Steam 사용법: **XINPUT EXE 비 Steam 게임 등록 + Steam Input 활성화**
