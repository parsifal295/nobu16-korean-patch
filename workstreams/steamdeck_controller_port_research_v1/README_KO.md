# Steam Deck 컨트롤러 경로의 PC 실행 파일 이식 가능성 조사

## 결론

이식 가능성은 높다. 다만 정적 분석 결과, Steam Deck 실행 파일에서
컨트롤러 드라이버 전체를 PC 실행 파일로 복사하는 방식은 필요하지 않다.
현행 PC 실행 파일에도 이미 Steam Deck 실행 파일과 같은 XInput 장치 열거,
상태 폴링, 버튼/축 변환 코드가 들어 있다.

실제 분리점은 여러 기능이 함께 사용하는 Steam Deck 런타임 판별이다.
두 실행 파일은 모두 Steamworks `ISteamUtils::IsSteamRunningOnSteamDeck()`와
일치하는 판별 함수를 호출한다. 이 반환값이 참이면 다음 동작들이 한꺼번에
활성화된다.

- XInput 장치에 대한 Steam Deck 전용 입력 보정
- 해상도 `1280 x 720` 강제
- 창 모드 값 `2` 강제
- Win32 텍스트 입력 대신 Steam의 게임패드/플로팅 키보드 경로 사용
- 일부 URL 및 동영상 경로의 Steam Deck 처리

따라서 Steam Deck 판별 함수 자체를 항상 참으로 만드는 전역 패치는
목표에 맞지 않는다. PC 해상도 설정 경로는 그대로 두고, 입력 관리자 안의
Steam Deck 조건만 선택적으로 참으로 만드는 것이 첫 번째 구현 후보이다.

정적 패치 후보는 확인했지만 이 조사 브랜치에서는 바이너리를 만들거나
Steam 설치본에 적용하지 않았다. 다음 단계의 격리된 런타임 검증에서
컨트롤러의 모든 버튼, 스틱, 포커스 전환 및 마우스 병행 동작을 확인해야
최종 이식 가능 판정을 완료할 수 있다.

## 조사 기준 바이너리

Steam 설치본의 현재 `NOBU16PK.exe`는 이미 패치된 67 MB 파일이므로 직접
비교 기준에서 제외했다. 같은 Steam 빌드의 보존된 원본 PC 실행 파일과
Steam Deck 실행 파일을 Steamless로 언팩한 결과를 Ghidra에서 비교했다.

| 구분 | 크기 | SHA-256 |
| --- | ---: | --- |
| 원본 PC `NOBU16PK.exe` | 31,978,264 | `29BC1ED66D27B9AEF5EB6CE3D126BA2BDBF86099E12B09615FE9F988F41E2246` |
| 원본 SD `NOBU16PK_SD.exe` | 31,969,048 | `6218F8987404BB20E1771D4E7BA032405DB9788C212F5E89F96B9AEFADA21FCD` |
| 언팩 PC | 31,747,848 | `BC885875A5E4288E5A1A424D99974F6F215777C03569C7EA707FDE63BDBC2B39` |
| 언팩 SD | 31,738,632 | `2411BF032F382FCD200D522E87A6D3551322CA28408518439003EB443CDF4A5B` |

설치된 게임의 Steam 앱 빌드 ID는 조사 시점에 `18823764`였다.

## PE 및 입력 계층 비교

두 언팩 실행 파일은 모두 x64 PE이며 같은 세 XInput 심볼을
`XINPUT1_3.DLL`에서 가져온다.

- `XInputGetState` (ordinal 2)
- `XInputSetState` (ordinal 3)
- `XInputEnable` (ordinal 5)

PC 실행 파일의 `.text`가 SD 실행 파일보다 `0x2000` 바이트 크지만,
추가 크기가 컨트롤러 모듈의 유무를 뜻하지는 않는다. 다음 핵심 함수는
전역 주소와 재배치된 내부 호출 주소를 제외하면 같은 동작을 한다.

| 역할 | PC VA | SD VA | 확인 내용 |
| --- | --- | --- | --- |
| XInput 장치 열거/생성 | `0x140FDFA80` | `0x140FE0000` | 최대 4개 패드 탐색, `XInputGetState`, `0x2A8` 바이트 장치 객체 생성 |
| XInput 상태 폴링/변환 | `0x140FE0720` | `0x140FE0CA0` | 진동 상태 전달, `XInputGetState`, 버튼·트리거·스틱을 내부 상태로 변환 |
| Steam Deck 판별 | `0x1409C07A0` | `0x1409C02E0` | Steamworks 인터페이스 vtable `+0x110`의 bool 메서드 호출 |
| 그래픽 설정 로드 | `0x1408B0000` | `0x1408AFC80` | 판별 결과에 따라 레지스트리 설정 또는 `1280 x 720`/모드 `2` 선택 |
| 입력 장치 후처리 | `0x140C5DE90` | `0x140C5E0B0` | 내부 키 코드 `0x27`과 `0`의 Deck 전용 상태 플래그 보정 |

Steamworks 공식 문서상 `ISteamUtils::IsSteamRunningOnSteamDeck()`는 Steam이
Steam Deck 또는 다른 SteamOS 기기에서 실행 중인지를 반환한다.

<https://partner.steamgames.com/doc/api/ISteamUtils#IsSteamRunningOnSteamDeck>

## 해상도 고정 경로

PC `0x1408B0000`과 SD `0x1408AFC80`은 같은 구조이다.

```text
if IsSteamRunningOnSteamDeck():
    width       = 1280
    height      = 720
    window_mode = 2
else:
    width       = Configs/WIDTH  (기본 1600)
    height      = Configs/HEIGHT (기본 900)
    window_mode = Configs/WINDOW_MODE
```

즉 해상도 고정은 SD 실행 파일에만 존재하는 별도 구현이 아니라 두 실행
파일에 공통으로 들어 있는 Steam Deck 런타임 분기이다.

## 선택적 입력 패치 후보

PC 입력 관리자 `0x140C5DE90` 안에서 Steam Deck 판별을 호출하는 두 지점이
첫 번째 최소 패치 후보이다.

| 호출 VA | 언팩 파일 오프셋 | 원본 5바이트 | 후보 5바이트 | 의미 |
| --- | --- | --- | --- | --- |
| `0x140C5E256` | `0x00C5D656` | `E8 45 25 D6 FF` | `B8 01 00 00 00` | 내부 키 코드 `0x27`의 Deck 입력 보정 활성화 |
| `0x140C5E292` | `0x00C5D692` | `E8 09 25 D6 FF` | `B8 01 00 00 00` | 내부 키 코드 `0`의 Deck 입력 보정 활성화 |

후보 바이트는 `call IsSteamRunningOnSteamDeck`을 `mov eax, 1`로 바꾸며
명령 길이를 그대로 유지한다. 해상도 함수의 판별 호출은 변경하지 않으므로
PC의 `WIDTH`, `HEIGHT`, `WINDOW_MODE` 설정 경로가 유지된다.

이 두 지점은 입력 장치 목록과 내부 입력 객체를 순회하고 장치의 입력 상태
플래그를 보정하는 함수 안에 있다. XInput 장치 열거와 폴링은 원래부터
항상 존재하므로, 우선 이 두 분기만 활성화하는 것이 가장 작은 실험이다.

## 전역 판별 패치를 피해야 하는 이유

PC 판별 함수 `0x1409C07A0`에는 입력 이외에도 최소 19개의 코드 참조가 있다.
대표적인 참조는 다음과 같다.

- `0x1408B0063`, `0x1408B0112`: `1280 x 720`, 창 모드 `2` 강제
- `0x1408B3519`: Steam Deck에서 그래픽 설정 저장 생략
- `0x1408C1EA7` 계열: Win32 편집 컨트롤 대신 Steam 플로팅 키보드 사용
- `0x140ACCE29`, `0x140ACCE71`: SD용 동영상 경로 조립
- `0x140571E22`, `0x140ED5596`: Steam Overlay URL 처리
- `0x140C5E256`, `0x140C5E292`: 입력 장치 후처리

판별 함수 본문을 항상 참으로 패치하면 컨트롤러 외의 모든 동작이 함께
바뀌며, 사용자가 피하려는 해상도 고정도 다시 발생한다.

## 다음 검증 단계

1. 원본 PC 언팩본의 별도 복사본에 위 두 5바이트 변경만 적용한다.
2. Steam 설치 경로가 아닌 격리 스테이지에서 실행 가능한 후보를 만든다.
3. PC 해상도를 `1920 x 1080` 이상으로 선택하고 게임 프로세스를 완전히
   종료한 뒤 재실행한다.
4. Xbox 호환 XInput 패드와 Steam Input 에뮬레이션 패드를 각각 시험한다.
5. 타이틀, 메뉴, 지도, 대화, 숫자/슬라이더, 텍스트 입력에서 다음을 기록한다.
   - A/B/X/Y, LB/RB, LT/RT, 십자키
   - 좌/우 스틱과 데드존
   - 버튼 아이콘 전환
   - 마우스와 패드의 동시 사용 및 포커스 복귀
   - 해상도와 창 모드가 PC 설정을 유지하는지
6. 두 호출점만으로 부족하면 XInput 폴링 결과와 상위 입력 이벤트를
   Frida로 추적하여 추가적인 Deck 전용 조건을 찾는다.

프로젝트의 런타임 이미지 QA 규칙에 따라 해상도를 바꾼 뒤에는
`NOBU16PK.exe`를 완전히 종료하고 재실행해야 한다. 모든 실게임 결과에
선택 해상도와 완전 재시작 여부를 함께 기록한다.

## 현재 판정

- 기술적 가능성: **높음**
- 필요한 작업 성격: 컨트롤러 코드 이식이 아니라 **기존 PC XInput 경로의
  선택적 활성화/Deck 분기 분리**
- 정적 패치 규모: 최초 실험 기준 **두 곳, 각 5바이트**
- 남은 불확실성: 두 입력 후처리 분기만으로 전체 UI 조작이 열리는지에 대한
  실게임 검증
- Steam 설치본 변경: **없음**
